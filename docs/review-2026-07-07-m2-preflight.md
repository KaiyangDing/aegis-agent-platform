## 0. 总体结论

**这套文档的体系性远超简历项目的常见水平，且文档与代码高度一致**：对账维度 10 项核对 9 项完全一致（133 测试、五类异常契约、提交哈希、CI 钉扎、报告凭证等全部命中，见 C44），唯一不符是 README 状态行过期（C16）。协作纪律（口径表、横切清单、凭证化数字）是真实在执行的，这本身就是项目最硬的资产。

**但评审发现三类系统性风险**，都集中在"即将开工的 M2 及其消费方"：

1. **跨层组合行为没人算过账**——L1 与 L2 各自设计都成立，但组合起来出问题：超时嵌套（C1）、熔断×fallback（C5）、异常契约×终止枚举（C6）、reaper×Redis 降级（C7）。单层评审全过，跨层一推演就穿。
2. **分布式正确性缺最后一块**——事件溯源+租约+锁的设计有骨架，但 fencing（C2）、降级锁语义（C4）、审批 CAS（C11）、跨副本事件通知（C22）这些"假死/并发/多副本"角落没封口。这恰是面试深挖必到的角落，且文档自己把面试官往这些角落引（ADR-005 主动提 Kleppmann）。
3. **面试叙事有几处自设的暴雷点**——AI 作者身份无答案（C3）、LangGraph 表述失实+占位符未填（C18）、对照组缺 Temporal/Dify（C19）、最稀缺卖点 replay 在简历和 demo 里双双缺位（C33）。

**好消息是：44 条里没有一条需要推翻已有架构**。绝大多数是"口径决策 + 文档落档"（半天级），少数需要在 M2.2 建表时多加一两列、在 M2 步骤里多接一条线。修复窗口正好在 M2 开工前——这也是本次评审的目的。

## 2. 三条 Blocker 的展开（必须在 M2 开工前裁决）

### C1 · 慢失败（上游挂起）全链路未设防
L1 读超时 90s、重试总预算 60s、L2 单步闸门 90s——三个数字组合起来意味着：上游"连接成功但不出 token"（真实 LLM 事故最常见形态）时，L2 闸门先于 L1 超时触发，`CancelledError` 穿透（router 只捕 Exception 家族），熔断记不上账、重试预算数学上不可达（60<90）、fallback 轮不到。M1.13 的 100% 成功率实验只注入"首块前快失败"，对这个形态零覆盖。反方向若把 90s 理解为整调用时长，M5.2 自设的 20 tok/s 下 1800+ token 的健康长回答也会被误杀。**修复主体是口径决策**：拆分"首 token 超时"与"块间空闲超时"，写死 L1 单候选最坏耗时 < L2 单步预算的嵌套约束，故障注入器加"挂起/慢流"模式补一组实测。

### C2 · 租约恢复缺 fencing
进程假死（笔记本睡眠、断点、同步阻塞 90s）→ 租约与锁双双过期 → reaper 抢租恢复 → 原进程苏醒继续写事件。现有防线只有 `(session_id, seq)` 唯一约束，但冲突后行为未定义：旧写者可能先占住 seq 反而挤掉合法新写者；若按 M2.2 "PG 故障退避重试 3 次"的口径处理唯一冲突，双写更隐蔽。尤其注意：ADR-005 主动引用 Kleppmann 对 Redlock 的批评当面试加分项，而该批评的核心论点恰是 fencing token——文档自己把面试官引向这道题却没有答案。**M2.2 建表时落位**：lease_generation 列 + 事件写入事务内校验所有权 + 三条协议（续租失败即自毁 / 唯一冲突即围栏绝不重试 / write-ahead 成功是副作用前置）。

### C3 · "AI 辅助开发/作者身份"无答案
2026 年任何简历项目的必问题，且本项目 git 历史、文档风格使 AI 深度参与不可隐瞒也不必隐瞒——协作规约"用户亲手敲所有代码、每步理解自查、面试深挖题先答后补"本身就是最好的答案素材，但 05 号文档没有把它组织成可背诵的应答。**建议 05 增一节**："AI 是我的结对工程师和评审员，架构决策、取舍裁决、每一行代码的落盘和调试是我的"——并用协作规约的具体机制（清单对账、理解自查、亲手排错）作为证据支撑，化被动为主动。

## 3. 值得单独点名的几组 Major

- **分布式正确性组**（C4/C7/C11/C22）：降级锁 `pg_advisory_xact_lock` 是事务级的，撑不住跨多事务的整个 run，且 Python `hash()` 跨副本不稳定——降级期互斥直接失效；reaper 依赖 Celery beat，而 Celery broker 是 Redis，"Redis 全灭"降级叙事里 reaper 自身停摆没被登记；审批四路并发竞写 pending 无 CAS；重订阅通道"写事件的副本 ≠ 服务 GET 流的副本"之间没有任何通知机制（Redis pub/sub 或 PG LISTEN/NOTIFY 或轮询，一个都没选）。
- **M2 设计内部矛盾组**（C6/C8/C9/C10）：这四条不修，M2.2/M2.6/M2.7 会按自相矛盾或未定义的规格开工。
- **安全纵深组**（C12/C13/C14/C15/C23）：都不是"v1 不该做"，而是"文档声明了却没给机制"——JWT 谁签、RLS 之外的路径、用户级归属校验、间接注入检测、PII 归属区分。
- **面试叙事组**（C18/C19/C33 + C3）：ADR-003 是"为什么自研"的旗舰答案，其中"LangGraph 没有 replay"的表述在 2026 年是错的（checkpoint 本有 time-travel），"借鉴了它的 X 设计"的 X 还没填——深挖必穿；而真正稀缺的"确定性回放"却埋在简历第 4 条 bullet 里，精简版直接消失。

## A. 确认的发现（44 条，双票/单票对抗验证均存活）

### A.1 Blocker 级

#### C1 · 慢失败(上游挂起)模式全链路未设防:L1 读超时 90s 与 L2 单步闸门 90s 相等、重试总预算 60s 小于单次挂起,重试/熔断/fallback 在最真实的故障形态下全部不可达

- **严重度**：blocker ｜ **类别**：失败哲学/跨层超时预算 ｜ **来源维度**：architecture
- **位置**：03 §2 终止条件表 / 00 §6.1 M2.7 / 02 §4;代码 gateway/providers/base.py(shared_client)、gateway/resilience.py(RetryPolicy)
- **证据**：03 §2:「单步超时 | LLM 90s / 工具 30s」;providers/base.py:「连接 5s(网不通要快速失败)、读取 90s(LLM 生成慢是正常的)」;resilience.py:「total_timeout: float = 60.0 # 重试总预算」;router.py FaultInjector:「只在首块前注入(模拟连接阶段失败)」;breaker.py:「probe_ttl…必须 ≥ 读超时 90s」。全部文档中没有任何一处定义 L1 内部最坏耗时与 L2 单步预算的嵌套关系,也未定义 90s 是『到首 token』还是『整次调用』。
- **影响**：上游挂起(连接建立但不出 token——真实 LLM 供应商事故的常见形态)时:候选 1 第一次尝试的 90s 读超时尚未到期,L2 的 90s 闸门已先触发并取消调用;CancelledError 不入 router 的 except 分支,熔断永远记不上账;重试(60s<90s)与 fallback 永远轮不到。结果是每个请求都干等 90s 失败、无快速失败、无换路,且下一个请求原样重复。M1.13 的 100% 成功率实验只注入首块前的快失败,故障注入工具没有『挂起/慢流』模式,该盲区无任何实验覆盖。M2.7 即将按未定义语义实装闸门 #2;面试一句『上游挂死 120 秒你的系统会怎样』即打穿『重试→熔断→fallback』的核心简历叙事。另一方向:若 90s 按整调用理解,M5.2 自己假设的 20 tok/s 下 1800+ token 的健康长回答也会被误杀。
- **建议**：M2.0 开工前敲定并写进 00 §2.2 口径表:① 拆分 L1 超时语义——首 token 超时(建议 15–30s)与块间空闲超时(如 30s)两个参数,整流时长不设上限;② 明确 L2 闸门 #2 的 90s 定义为『到首块』或改为空闲型超时,并强制嵌套约束『L1 单候选最坏耗时(含重试退避)< L2 单步预算』;③ 网关 complete() 支持调用方传入 deadline(LLMRequest 加字段)向下传播;④ M2.12/M5.4 故障注入增加『挂起/慢流』注入模式并补一组实测数字。
- **验证者补充**：发现成立，所有 evidence 逐字核实无误且无断章取义。核实细节：(1) 03 §2 L49 确为「LLM 90s / 工具 30s」，全部 8 份文档+7 份 ADR 无任何一处定义该 90s 是到首 token、整调用还是空闲型，也无 L1/L2 嵌套约束；00 §2.2 口径表、§10.1 十六项遗留、§10.3 裁剪表、§11 砍法均未登记此问题。(2) 代码核实：base.py L43 httpx read=90.0；resilience.py L39 total_timeout=60.0，且 L70 的预算检查意味着单次 90s 挂起后 elapsed>60 直接 raise——重试在挂起形态下数学上不可达；router.py L256-275 只 catch ProviderError 家族子集，CancelledError（BaseException）必然穿透，L2 取消时 breaker.on_failure 永不执行；FaultInjector L114 自注释「只在首块前注入」，无挂起/慢流模式；breaker.py L42 probe_ttl 注释确实自证了「读超时 90s」是系统隐含耦合参数。(3) 竞态方向确定：L2 单步计时还包住上下文组装+租户限流 wait_take max_wait=10s+connect 5s，90s 必先于 L1 读超时到…

#### C2 · 租约恢复缺 fencing 机制：假死写者与 reaper 新写者的双写窗口只靠 (session_id,seq) 唯一约束兜底，冲突后行为未定义

- **严重度**：blocker ｜ **类别**：事件溯源/并发正确性 ｜ **来源维度**：runtime-harness
- **位置**：03 §5；00 §6.1 M2.2/M2.10
- **证据**：03 §5:"seq 由持会话锁的单写者在事务内递增,(session_id, seq) 唯一约束是并发写入的最后防线";"reaper(Celery beat 周期任务)扫描'租约过期且 run_state=running'的会话,抢租后触发恢复"。全部文档未定义:① 续租/锁续期失败时原 loop 的自毁义务;② 唯一约束冲突后的语义(被围栏 or 可重试故障);③ 事件写入事务内对租约所有权的校验。00 §6.1 M2.2 还规定"事件写入短退避重试 3 次仍失败 → 终止本次 run",未把唯一约束冲突从可重试的 PG 故障中区分出来。
- **影响**：原进程假死而非死亡(笔记本睡眠、调试断点、事件循环被同步调用阻塞在 90s LLM 步内)时,Redis 锁 TTL 与 PG 租约双双过期,reaper 抢租恢复,随后原进程苏醒继续写事件:若旧写者先占住 seq N,合法持租的新写者反被唯一约束拒之门外,事件日志被两个发散上下文交错污染;旧写者还能在自己的 write-ahead 插入成功后执行新的工具副作用。若实现按 M2.2 口径把唯一冲突当 PG 故障退避重试 3 次,双写更隐蔽。这是租约设计的第一道面试追问("租约过期但原进程还活着还在写怎么办"),现有答案挡不住;事后补救 = events/sessions 表迁移 + M2.10 恢复逻辑返工。

#### C4 · 会话锁 Redis 降级方案 pg_advisory_xact_lock(hash(session_id)) 双重硬伤：事务级锁在首个事件事务提交即自动释放、无法覆盖跨多事务的整个 run；Python hash() 跨副本不稳定使降级期互斥直接失效

- **证据**：00 §6.1 M2.9:「Redis 不可用降级为 PG advisory lock——pg_advisory_xact_lock(hash(session_id)),保住互斥而非放弃,停 Redis 验证纳入本步测试」;02 §2③:「锁被占(上一条还在处理)→ 返回 409」——锁必须覆盖整条消息的完整处理(一次 run,分钟级、横跨多次事件写事务,M2.2『事件写入短退避重试 3 次』即每步独立事务);03 §5:「seq 由持会话锁的单写者在事务内递增」(单写者前提=锁覆盖整个 run);而 pg_advisory_xact_lock 在持锁事务结束时自动释放,三份文档均为同一写法。另:Python 内置 hash() 对字符串按进程随机加盐(PYTHONHASHSEED),且 advisory lock 键是 bigint,hash(session_id) 的具体映射未定义。
