## M0 · 工程底座（0.5 周）

**交付物**：GitHub 仓库初始化（**.gitignore 在第一个提交就包含 `.env`**，密钥永不入库）、
uv 工程（`pyproject.toml` + `uv.lock` 入库，ruff + mypy + pytest 为 dev 依赖）、分层目录、
分环境配置（pydantic-settings，dev/staging/prod）、docker-compose（PG+pgvector ≥0.8、Redis）、
GitHub Actions（setup-uv + lint + 测试）、import-linter 强制分层依赖方向。

**验收**：`docker compose up` 一键起基础设施；CI 全绿；故意写一个 L1 import L3 的文件，CI 必须失败。

## M1 · L1 LLM 网关（2 周）

**交付物**：
- 供应商适配器 ×2：`openai_compat.py`（百炼兼容模式，覆盖 Qwen 全系与平台上的 DeepSeek）
  + `anthropic.py`（完整实现、桩测试——暂无真实 key，接入即用；若后续获得第二平台真实 key，
  跨平台 fallback 演示随即升级为真实）；
- 档位映射配置：fast=qwen-flash/turbo、standard=qwen-plus、strong=qwen-max
  （以 M1 时百炼模型列表实测为准，映射是配置不是代码）；
- **统一 tool-call 抽象**（`schema.py`：LLMRequest/LLMChunk + 各供应商双向映射，
  含中途换供应商时历史 tool_call/tool_result 消息的格式转换）——这是 M1 实现量最大的单项，显式占 3–4 天；
- 档位路由；超时（连接/读取分离）；受控重试（无副作用前提 + 错误码白名单 + Retry-After + 重试预算）；
- 熔断器（Redis 共享状态 + 半开探测互斥令牌）；按档位 fallback 矩阵；
- 出站限流（Redis 令牌桶 Lua，供应商/租户两维度，压测脚本自写，计 0.5 天）；
- 精确缓存（tenant_id 前缀 key）；usage_ledger 计量（明细到请求）；
- **故障注入开关**（配置化随机失败率，供演示与测试）。

**验收（量化，注明实验口径）**：
- 故障注入实验——设定写死：仅对主供应商注入 30% 失败、最大 3 次尝试、1 层同档 fallback；
  1000 次调用报告**成功率与 P50/P99 两组数字**（目标成功率 ≥99%，可靠性-延迟代价一起呈现）；
- 熔断：打开期间对故障供应商**穿透请求数 = 0**；上游恢复后 X 秒内自动闭合（X 实测记录）；
- 限流精度误差 < 5%；
- 对账脚本能从请求明细汇总出租户/会话/模型/天四个聚合维度。

**面试考点**：为什么 429 要读 Retry-After；为什么"幂等错误"是错误用词（重试前提是请求无副作用）；
熔断状态为什么放 Redis、半开探测怎么防惊群；跨供应商 tool-call 协议差异怎么抹平。

## M2 · L2 Agent 运行时（2.5 周）——技术含量最高的一段

**交付物**：AgentLoop（7 类终止条件 / 6 道闸门）；ContextBuilder（分层预算 + 滚动摘要）；
工具注册（装饰器 + risk_policy 条件闸门 + docstring 生成 schema）+ ToolExecutor
（校验/权限三层/write-ahead 幂等/超时/截断）；EventStream（schema_version + 单写者 seq）+
投影同事务派生；**恢复调度**（租约 + reaper + 恢复单入口）；Guardrails v1（含流式增量检查）；
**FakeGateway 录制回放**（显式 2–3 天：cassette 格式、匹配键 = 会话 id+轮次、重录流程文档、
录制基准会话集为一次性真实调用并写明预算上限）。

**验收（量化，口径可测）**：
- 6 道闸门各有单测，含"诱导死循环"对抗用例；
- **回放模式下**：中断-恢复后的事件序列与不中断运行**逐事件一致**（强断言，进 CI）；
- **真实模型下**只断言不变量：无重复副作用（tool_invocations 幂等键核验）、事件 seq 连续合法、
  到达合法终止条件（LLM 输出非确定，"结果逐字一致"不可测，不承诺）；
- 30–40 轮长对话（cassette 夹具制作计入排期）触发 ≥2 次滚动摘要，且能答出第 1–5 轮埋入的关键事实；
- **必保路径：HITL 挂起-恢复**（审批回调 → 状态翻转 → 单入口恢复）；
  kill -9 崩溃恢复为同路径的扩展验证，排 M2 末尾、紧张时顺延到 M4；
- 运行时测试全程零真实 API 调用。

**面试考点**：事件溯源 vs 快照；write-ahead + 幂等键透传为什么才是真幂等；
恢复由谁调度（租约/reaper/锁单入口）；上下文压缩丢信息怎么办（摘要用于 prompt、events 原文兜底）。

## M3 · L3 客服业务（2 周）

**交付物**：
- 摄取流水线（Celery：解析→切块→text-embedding-v4 批量调用（限流/重试/断点续传）→入库）；
- 多租户检索（WHERE + RLS 兜底；`hnsw.iterative_scan` 或小租户精确扫描）；
- **RLS 策略 + 连接池租户上下文注入（SET LOCAL 事务钩子 + 低权连接角色）**——显式列条，
  与 SQLAlchemy async 集成有已知坑，预留 1–2 天；
- 意图路由（FAQ 直答/RAG/工具/转人工四分类）；
- 模拟业务系统（进程内 FastAPI 子应用，延迟/错误率注入可配）+ 工具五件：
  orders / logistics / tickets / refunds / coupons（优惠券复用退款骨架，半天）；
- HITL 审批流（expires_at 超时 + 用户撤回 + 批准后前置校验重跑）——API + curl 演示，审批页 stretch；
- SSE 聊天页（POST 流 + 重订阅通道 `GET /v1/sessions/{id}/stream`）；转人工与兜底话术；
- **种子评测集 15–20 条**（≥10 条租户隔离对抗 + 5 条知识库外问题）——M3 验收自用，M4 扩充；
- 演示语料与种子数据：每租户 10–20 篇文档 + 种子订单脚本（1 天）。

**验收（量化）**：
- 对抗用例全绿：跨租户检索不可见；**租户 A 高频问题在 B 侧缓存不命中**；
  水平越权（用户 A 报用户 B 订单号退款）被拒；**租户 A 坐席审批租户 B 审批单 → 403**；
- 精确缓存命中 < 50ms；未命中首 token < 2.5s（本地环境口径，实测修正）；
- 退款超租户配置阈值（演示值 200 元）必挂审批；审批期间用户收到 `approval_pending` 提示；
  批准后先重跑前置校验再执行、自动续跑；超时/撤回路径各演示一次；
- 知识库外问题在种子集上兜底/转人工触发率 **≥95%**，未触发的逐条人工归因
  （"100% 零编造"不是可验收指标——LLM 幻觉无法保证绝对消除，写绝对值反而是被攻击点）。

**面试考点**：意图路由为什么用小模型；切块策略对召回的影响；HITL 挂起状态存哪、
超时未审批怎么办（expires_at + reaper + approval_expired 事件）；RLS 在连接池下为什么必须 SET LOCAL。

## M4 · 治理层（1.5 周）

**交付物**：
- trace 查询 API（JSON，凭 trace_id 还原全链路；查看页 v2）；
- Prometheus 指标（成功率/P50/P99/token/工具成功率/转人工率/缓存命中率）；
- **评测双流水线（评审后拆分，两者目的不同不可混）**：
  1. **CI 回放回归**（每次提交，零 token）：断言**行为轨迹**——终止原因、工具调用序列、
     隔离/预算硬约束；prompt 变更的 PR 必须附带重录 diff（重录流程 M2 已定义）；
  2. **离线质量评测**（真实调用 + LLM-as-judge，nightly/手动触发）：单次预算上限写死在配置，
     judge 用 strong 档，三类用例（检索质量/端到端/对抗）各有判据文档；
- 评测集从种子 15–20 条扩充到 **30–50 条**；
- **成本对照实验（两组分开，各自口径干净）**：
  1. 档位路由降本：全唯一问题集上测（不受重复率污染）；
  2. 精确缓存降本：声明分布假设的模拟流量（如 30% 问题为历史复述）单独测；
  产出两个实测数字 + 实验口径说明，**不预设目标值**（"≥40%"这类可被评测集构成操纵的预设已删除）。

**验收**：凭 trace_id 还原任一会话每步输入输出与耗时；CI 回放回归红绿有效
（故意改坏一个硬约束，CI 必须变红）；两组成本数字 + 口径报告产出。

**面试考点**：为什么回放测行为、真实调用测质量，两者不可互替；LLM-as-judge 的偏差怎么校准；
成本数字怎么做到"没法被质疑是评测集凑出来的"。

**与 OpenTelemetry 的关系（2026-07-07 评审 C37 落档）**：自研 trace（events 即 trace 源）而非
接 OTel 是刻意选择——本项目的 trace 单位是"会话/run/事件"这一业务语义层，OTel 的 span 模型
面向跨服务 RPC 树，单体 + Celery 的拓扑里 collector/exporter 的运维负担大于收益。两者不互斥：
映射关系已清晰（session=trace、run=root span、事件=span event），obs 的查询 API 是稳定接口、
换后端不动调用方，v2 可加 OTel 导出器。面试一句话："我需要的是 LLM 语义的可观测
（token/工具/终止原因），先做业务 trace；OTel 是导出格式问题，不是设计问题。"

### M1 代码审计追加项（2026-07 四视角审计后落档）

- **M1.12 增补交付物**：Redis 不可用降级（02 §5 承诺的"停 Redis 容器核心链路不断"）——
  limiter 降级进程内令牌桶（速率=全局/副本数）、breaker 降级 fail-open + 本地计数
  （语义补进 ADR-005）、与故障注入实验共用"停容器"演示；实验报告须注明出站限流
  计数口径为"按 HTTP 调用"（重试的第 2/3 次尝试暂不过闸）；
- **M1.11 范围注明**：三级预算闸门归属——单请求/租户月度在 L1（依赖 usage_ledger 聚合），
  会话级在 L2 终止闸门；本步至少交付租户月度闸门的读路径。

## M5 · 交付收口（1 周）

**交付物**：locust SSE client（自写，1 天）；压测报告**两组口径分开**：
1. 平台开销与并发容量：FakeGateway 注入固定延迟模型（首 token 800ms + 20 tok/s），
   压本地多副本，报告吞吐/错误率/平台自身开销 P50/P99；
2. 真实延迟分布：小样本（50–100 次）真实调用测首 token 分布，不做高并发（费用与厂商限流约束）；
`--scale api=3` + Nginx 水平扩展演示；15 分钟 demo 脚本（故障注入、断点续跑、多租户隔离三个高光时刻）；
README 终稿 + 架构图 + 简历数据回填。

**验收**：demo 脚本实测 ≤15 分钟跑通全部高光时刻；压测报告覆盖 ≥3 个并发档位、两组口径分开呈现；
简历模板中所有 X 占位符已回填实测值（简历表述限定"本地压测（模拟上游延迟）下 P99 …"）。
