## 2. 项目叙事线（"介绍一下你这个项目"的 90 秒版本）

1. **问题**：原型 Agent 和企业可用之间隔着七类工程问题——循环失控、工具不可信、上下文爆炸、
   上游故障、并发与成本失控、不可观测、不安全（各文档统一用这七类，背稿以此为准）；
2. **方案**：三层平台——网关层解决"调模型"的可靠与成本，运行时层解决"跑 Agent"的可控与可恢复，
   业务层解决"做客服"的数据与权限；分层纪律用 CI 强制；
3. **亮点抓手**（挑一个展开）：事件溯源让 HITL 恢复和崩溃恢复共用一条代码路径、日常流量天天在测
   灾难恢复；或：故障注入下的熔断 + fallback 实测；或：成本对照实验的干净口径；
4. **结果**：量化指标 + 15 分钟可复现 demo。

## 3. 面试深挖问答索引

每个问题的完整答案都在对应文档里，面试前按此表复习：

### 架构类
| 问题 | 答案位置 |
|---|---|
| 为什么要平台，不直接调 API？ | ADR-001；"LLM 是 CPU，平台是操作系统" |
| 为什么单 Agent 而不是多 Agent？ | ADR-002；读密集可并行才受益，主链路要一致性；接口已预留 v2 |
| 为什么自研不用 LangChain/LangGraph？ | ADR-003；含"框架不是不能用"的辩证答法 |
| 三层怎么保证不互相渗透？ | 架构 §1；依赖单向 + import-linter CI 强制 |

### 运行时类
| 问题 | 答案位置 |
|---|---|
| Agent 死循环怎么防？ | 运行时 §2；六道闸门 + 重复调用哈希窗口 |
| 上下文超长怎么办？压缩丢信息怎么办？ | 运行时 §3；摘要只服务 prompt，events 原文是事实源 |
| LLM 生成的参数能直接用吗？ | 运行时 §4；Pydantic 校验 + **LLM 可控参数与运行时注入 ctx 分离** |
| 工具怎么做到真幂等？ | 运行时 §4；write-ahead 事件 id 透传下游去重；本地缓存只是加速；为什么裸 order_id 做键是错的 |
| 任务跑一半崩了怎么办？**谁**来恢复？ | 运行时 §5；重放语义 + 恢复调度（租约/reaper/锁单入口）分开答 |
| 流式输出了一半崩了，用户看到什么？ | 运行时 §5；半截 llm_call 作废重发 + 消息重置帧，诚实承认文本可能不同 |
| 怎么调试一次坏掉的会话？ | 运行时 §5 + M4；trace_id 重放 |

### 可靠性 / 并发类
| 问题 | 答案位置 |
|---|---|
| 供应商挂了怎么办？ | 架构 §4；受控重试→熔断（半开互斥）→按档位 fallback 矩阵，故障注入实测 |
| 为什么"重试幂等错误"是错误说法？ | 架构 §4；幂等是请求属性不是错误属性；错误码白名单 + 重试预算 |
| 为什么 async 不用多线程？GIL 影响？ | ADR-004；资源成本差数量级（不是"不可行"）；GIL 限制纯 Python 字节码的 CPU 并行，C 扩展除外 |
| Redis 在系统里干什么？挂了怎么办？ | ADR-005；六个角色；锁降级为 PG advisory lock（不放弃互斥） |
| 分布式锁怎么释放才安全？ | ADR-005；owner token + Lua compare-and-delete（比 Redlock 更基础的必考题） |
| 同一会话并发两条消息？ | 架构 §2；会话锁 + 409 策略；awaiting_approval 的消息准入另有规则 |
| PG 挂了怎么办？ | 架构 §5；事实源不可用 = 服务不可用，显式接受并快速失败——这也是答案 |

### 成本 / 质量类
| 问题 | 答案位置 |

### 安全类
| 问题 | 答案位置 |
|---|---|

## 4. "AI 辅助开发 / 这是你自己做的吗"（2026 年必问——主动讲；2026-07-09 按真实工作流校订）

> 2026-07-07 评审 C3（blocker）落档：git 历史与文档体量使 AI 深度参与不可隐瞒也不必隐瞒，
> 无准备的支吾比 AI 参与本身杀伤力大得多。立场：**不隐瞒、不缩水、化被动为主动**。

**90 秒标准答案**：

1. **分工**：AI 是我的结对工程师和评审员——出初版代码与设计草案、做多视角对抗评审；
   **架构决策、每一处取舍的裁决、每一行代码的落盘、全部调试排错是我亲手做的**
   （协作规约写死：每次交付我亲手敲、亲手执行，报错先自己读 traceback 给出"我觉得是 X
   因为 Y"再讨论）；
2. **证据**：提交历史是小步、单主题、message 写"为什么"的真实节奏；模块收尾我先答
   面试深挖题、AI 补充；我抓出过 AI 的真实缺陷（验收范围过宽、"content 为 null 不会
   KeyError"误判、**降级熔断半开违反自家不变量**（复盘揪出，两步重构）、**限流降级每调用
   付 ~3s 重试税**（我主动停 Redis 压测暴露，修复后 0.19% 有凭证））——**能指出 AI 的错，
   才证明理解在我**；
3. **观点收尾**："企业里 AI 辅助已是默认工作方式。会用 AI 不是风险，不会验证 AI 才是——
   这个项目的验收纪律（清单对账、凭证化数字、对抗评审）就是我对'怎么验证 AI 产出'的答案。"

**追问"哪段代码不是你写的"**：如实分层答——"生产代码**除 M2.10（恢复调度）由 AI 直写、
我逐 diff 审查验证提交外**，其余全部我亲手敲入、亲手排错，初稿多有 AI 参与
（2026-07-17 规约单步例外，00 §2.1 括注留档——表述逐词诚实）；测试代码自 M2.2③ 起由 AI
起草直写，我定验收口径并逐项对账（2026-07-09 规约修订）；挑任何一个模块我都可以白板
重写核心逻辑"——并主动把最难的模块（熔断半开互斥、事件溯源恢复、租约 fencing）递给对方挑。

**追问"AI 使用率多少"**：不报单一百分比——"初稿行数占比很高，我不装；我连 AI 的 token
账单都记着（M1 阶段输入 1.29 亿 token、96% 缓存读）：这个项目本身就在做 LLM 计量，
我对自己的用量用同一套纪律"。有意义的分界不是行数是权力：**架构裁决、口径决策、
验收、缺陷发现 100% 在我**。
