## 2. 协作规约操作化（权威文本 00 §2.1，此处翻译成可执行动作）

### 2.1 分工矩阵

| 事项 | 谁做 | 谁看/谁裁决 | 产物形态 |
|---|---|---|---|
| 生产代码（`aegis/` 包） | **用户亲手敲** | AI 给完整代码+逐段解释；用户敲入 | 交付正文里的代码块（含"为什么"注释），**AI 绝不直接写入产品文件** |
| 测试代码（`tests/`） | **AI 直接写入/修改**（2026-07-09 修订） | 用户看交付里的测试讲解 | Write/Edit 直接落盘 + 交付正文中的讲解 |
| 文档/计划/记忆 | AI 直接维护，口径变更**当天落档** | 用户随时可质疑 | 直接落盘（00/plans/记忆档案等） |
| 验证与 git 指令 | **用户执行** | AI 给完整指令块+每条预期结果 | 2.3 的标准指令块（ruff format 必须包含——曾长期漏给） |
| 架构与口径裁决 | **用户拍板** | AI 给建议+理由，绝不代替裁决 | 交付里的【用户拍板】项；裁决结果当天落 00 §2.2 |

### 2.2 交付四件套骨架（每次交付照此模板，缺件=交付无效；排错表已于 2026-07-09 取消）

```markdown
## 交付 M2.x①：<主题>

### 一、设计讲解
- 架构位置：<L1/L2/L3 哪层、与谁缝合>
- 文档锚点：<00 §x / 03 §x / plans/m2.x-….md §x>
- 为什么这么设计：<关键取舍，2–4 条>

### 二、完整代码 + 逐段解释（用户亲手敲入）
文件：`aegis/runtime/xxx.py`（新建/修改）
<完整代码块，关键行带"为什么"注释>
<逐段解释：每段 2–5 句，讲清楚"这段在防什么">

### 三、落盘与指令块
- 测试文件已由 AI 直接写入：`tests/runtime/test_xxx.py`（N 个测试，逐个点名）
- 用户落盘生产代码后执行：<2.3 标准指令块>

### 四、验收清单对账
- [ ] 新增文件逐项点名：<路径列表>
- [ ] 新增测试逐项点名：<test_xxx / test_yyy …，共 N 个>
- [ ] pytest 收集数：基线 B → 预期 B+N
- [ ] 本步对应 00 §6.1 表格行的哪些字：<引用原文>
```

### 2.3 标准指令块模板（仓库根（本 repo） 执行；预期输出为 2026-07-10 实测）

```powershell
uv run ruff format .    # 预期：N files left unchanged（若有文件被改写=交付代码未过格式化，回报 AI）
uv run ruff check .     # 预期：All checks passed!
uv run pytest -q        # 预期：<基线+新增区间> passed（如 301 基线 + 本步预告 n → “30x passed”）
uv run mypy .           # 预期：Success: no issues found in 66 source files（文件数随交付增长）
uv run lint-imports     # 预期：Contracts: 1 kept, 0 broken.
git add <本步点名的文件，逐个列出，不用 git add .>
git commit -m "<type(scope): 主题>" -m "<为什么做这一步>"
git push                # 预期：推送成功；GitHub Actions 全绿后本步才算落地
```

### 2.4 「验收」关键词的语义

- **只有用户说"验收"，AI 才代跑核对**（pytest/对账脚本等）；平时 AI 只给指令块，由用户执行；
- 验收动作 = 清单对账：逐项点名新增测试/文件 + pytest 收集数核对；
- **提交落地属于验收**（00 §2.1 第 8 条）：一步没 commit+push 就不算完成；
- 禁语：对未核查部分说"全部正确"（见 §4 第 10 条）。

### 2.5 会话切换规则（2026-07-10 修订，已同步 00 §2.1 第 12 条）

- **里程碑边界**：00 §13 毕业清单 **6 项全部勾完**才切换；
- **步边界**（超长会话时允许）：该步已收口（提交+推送+对账完成）**且**记忆档案与 00 §6.3 已更新；
- 切换前必做：记忆档案重写为当前状态；新会话从 §1 启动协议开始。

## 4. 高发错误模式与对策（本手册的灵魂；每条：场景→错误行为→正确行为）

1. **凭记忆写接口**（弱模型第一大坑）
   场景：交付代码要调用既有类/函数。错误：凭记忆或凭文档转述写签名。
   正确：**先 Read 真实源码核实**（CLAUDE.md 硬规则 8）——文档只是导航，签名以 `文件:行号` 为准；
   plans/ 计划文件里的签名也要过 §0 开工核对清单再信。

2. **交付正文放在工具调用之间被客户端吞掉**（2026-07-09 M2.3① 真实事故：生产代码整段蒸发）
   场景：一个回合里既有工具调用又有交付正文。错误：讲解/代码/指令块夹在两次工具调用之间。
   正确：**交付正文必须是回合最末、所有工具调用之后的最终消息**；顺序固定为
   "测试落盘等工具操作先做 → 交付文本最后发"。（来源：记忆档案·关键教训）

3. **Edit 子串误匹配粘行**（用户曾现场抓出）
   场景：Edit 修改源文件。错误：old_string 取过短子串，匹配到相似前缀，改错位置或两行粘连。
   正确：old_string 带足上下文保证唯一；改完看 Edit 返回的上下文确认落点。（来源：记忆档案）

4. **预告收集数错报**（M2.4① 真实事故：预告 12 实为 11）
   场景：四件套里报"本步新增 N 个测试"。错误：数个大概。
   正确：**逐项点名每个测试函数名之后再数**；验收时用 `pytest -q --collect-only` 末行对平。
   （来源：00 §6.3 M2.4 行偏差登记）

5. **估算 vs 测量翻车**（workflow token 事故）
   场景：需要报任何数量（token/行数/耗时）。错误：拍脑袋估算当测量报。
   正确：能测量就测量；估算必须标注"估算"二字——项目口径本身就是"护栏用估算、账单用实测"（C25）。

6. **PyCharm 装包毁 pyproject**（booktype 事件，记忆索引 pycharm-uv-install-hazard）
   场景：缺依赖。错误：PyCharm"安装包"按钮（在 uv 工程里触发 uv add 改坏 pyproject，曾覆盖坏 redis-py）。
   正确：**只用 `uv add <pkg>` / `uv add --dev <pkg>`**（06 §3）；发现来历不明依赖先 `git log -S` 查来源。

7. **脚本落盘 cwd 落错位置**（记忆索引 script-output-anchor-project-root）
   场景：写实验/演示脚本要落文件（如 `reports/`）。错误：相对路径依赖 cwd（PyCharm cwd=脚本目录）。
   正确：`Path(__file__)` 锚定项目根再拼路径；审查落盘代码时主动查这一点。

8. **PowerShell 中文乱码两刀**（06 §4 第 3 坑，2026-07-07 实测踩中）
   场景：Python 输出经管道落盘凭证。错误：直接 `脚本 | Tee-Object 文件`。
   正确：两端钉 UTF-8（`[Console]::OutputEncoding = UTF8` + `$env:PYTHONUTF8="1"`，已进 $PROFILE）；
   落盘用 `Out-File -Encoding utf8`（PS 5.1 的 Tee-Object 默认 UTF-16，git 当二进制）；根治=pwsh 7。

9. **redis-py 8 默认重试拖垮请求**（复盘补丁二，2026-07-08）
   场景：新增 Redis 触点。错误：自建客户端用库默认参数（retries=10+指数退避，一次故障拖 ~3s）。
   正确：**一律复用 `aegis/core/redis.py` 的 `get_redis()` 共享客户端**（connect 1s / read 2s /
   `Retry(NoBackoff(), 1)`，redis.py:22-24）；新触点的降级是否粘滞化见 00 §10.1 #29（M4.0 复核）。

10. **对未核查部分说"全部正确"**（禁语）
    场景：验收对账。错误：核对了 3 项就说"全部通过"。
    正确：只对逐项点名核对过的下结论；没核对的显式写"未核查"。（00 §2.1 第 9 条）

11. **一次交付多步 / 顺手重构**
    场景：改 A 时看见 B"可以顺手改好"。错误：一个交付里塞两步、或未经拍板的重构混进 diff。
    正确：**每次交付只给一步**（00 §2.1 第 5 条）；重构单列提案给用户拍板；范围先对 00 §10.3。

12. **把 06 §7 旧"五件套"当现行规约**
    场景：读到 06 §7 的"每步交付五件东西（含常见报错排查）"。错误：照它执行。
    正确：06 §7 已标注被取代（2026-07-10 注记）——现行是 **00 §2.1 四件套**，排错表 2026-07-09 取消。

## 5. 口径速查卡（00 §2.2 全表一行式摘要；正文以 00 §2.2 为准，此处只给"何时必须回读"的触发条件）

| 口径（00 §2.2 行名） | 一行摘要 | 必须回读原文的触发条件 |
|---|---|---|
| 失败哲学分野 | 安全闸 fail-closed / 成本闸 fail-open / 缓存计量绝不拖垮请求 | 任何新闸门、新降级路径设计时 |
| 半截不换路 | 首块后只能诚实中断（`GatewayStreamInterrupted`+`__cause__`）；L2 镜像=半截 llm_call 作废重发 | 碰流式、恢复、重发逻辑时 |
| 网关异常契约 | L2 只见三组六类；ProviderError 永不穿出网关 | 写任何 `except` 网关异常的代码时 |
| 熔断记账 | 429 不进熔断账；熔断 provider 粒度 | 碰熔断/限流/异常分类时 |
| 数据访问 | 报表裸 SQL、实体 ORM；值 lru_cache、资源手动 global | 新增查询或单例时 |
| 测试纪律 | 时序断言不进 CI；测试目录镜像源码分层 | 写任何含时间量断言的测试时 |
| 安全底线 | 密钥环境变量+打码 / .env 不入库 / prod 禁注入 / 绑 127.0.0.1 | 碰配置、日志、compose、错误文本时 |
| 术语统一 | 终止条件 7 类，对外说"六道终止闸门" | 写文档/注释/简历提终止条件时 |
| 简历数字纪律 | 没实测不写数字；数字必有凭证+口径 | 写任何对外数字时 |
| 上下文成本意识 | M1 实测输入 1.29 亿 token（96% 缓存读） | 讲上下文工程动机时（引用此数据） |
| 超时语义（C1） | 三段：connect 5s / 首 token 25s / 块间空闲 30s；deadline 向下传播 | 碰任何超时参数、压测延迟模型时（M5.2 改延迟模型前必读） |

## 8. 用户画像与沟通约定

- **学习者模式**：用户是求职者/学习者，目标是面试可辩护性——每个设计都要能被他复述与捍卫。
  概念讲解用**类比 + 代码 + 场景三件套**（记忆档案验证有效），讲到"可复述"为止。
- **先问为什么**：用户会先问透"为什么"再动手。AI 给方案必须带理由与取舍，不给"就这么写"式指令。
- **随时可质疑设计**：改文档比改代码便宜。用户质疑时认真复核，**别嘴硬**——他抓出过 AI 的真实缺陷：
  验收范围过宽、"content null 不会 KeyError"误判、Edit 前缀误匹配、降级熔断半开违反自家不变量
  （后者成为面试素材：同一半开语义三代实现）。被抓出错误照实认账并当天落档。
- **报错提问范式**：用户先自读 traceback，以"我觉得是 X 因为 Y，对吗"发问——AI 先评判他的假设
  （对/错在哪），再给定位，不越过他直接甩修复代码。
- **深挖题不当场问答**：每模块收尾 AI 直接追加进 `docs/interview-questions.md`（格式见其头部：
  编号不重排、带答案指针）；用户开发完统一自测，先自己答、AI 补充批改。
- **AI 作者身份叙事约束**（05 §4）：面试立场是"不隐瞒、不缩水、化被动为主动"——事实基础是
  "生产代码全部用户亲手敲入、测试自 M2.2③ 起 AI 直写、架构裁决 100% 在用户"。
  **接续开发不得破坏这一事实基础**（比如替用户直接写产品代码），否则 05 §4 答法失真。
