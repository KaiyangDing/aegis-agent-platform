## §1 目标与定位

- **做什么**：新建 `aegis/runtime/context.py`，交付 `ContextBuilder`——把"每一轮进入 prompt 的内容"从无脑拼接变成**按预算编译**（03 §3：六层预算表逐层落到函数级），并实装**滚动摘要**（会话历史超预算时，最老一半轮次经注入的 fast 档摘要钩子压缩，产物以 `summary_updated` 事件入流、`sessions.summary` 由 M2.2 既有投影机制同事务派生——C8）。
- **为什么**：上下文是 Agent 系统第一大账单（00 §2.2"上下文成本意识"：M1 会话实测输入 1.29 亿 token）；同时它是 M2.7 AgentLoop 的直接上游——loop 每轮"组装上下文→调网关"（03:33-40），没有编译器循环无米下锅。
- **架构位置**：L2 运行时内部件。对上被 AgentLoop（M2.7，`loop.py`）持有调用；对下只读事件事实源/投影（store）+ 注入面（ContextConfig、providers、summarize 钩子），**不认识网关**（`GatewayLike` 不进本文件 import）。长期记忆/本轮检索两槽位只做注入 Protocol，实装归 M3.5（00 §10.1 #7）。
- **面试叙事**：三个考点在此落地——"prompt 是编译出来的不是拼出来的"；"上下文压缩丢信息怎么办：摘要只服务 prompt，events 原文永远兜底"（00 §6.2 面试考点）；"摘要为什么必须入事件流：LLM 产物不可确定重算，不入流则回放重建不出投影"（C8）。
- **与 M2.4 的分工边界（防重复实现）**：**单条**工具结果超预算的收缩（fast 档摘要/硬截断）已由 `ToolExecutor._shrink` 完成（executor.py:244-262），ContextBuilder 只消费其产物（ToolOutcome.content 已 ≤ result_token_budget）；本步只管**工具结果层的聚合**超预算（多条结果之和超 3k）——用确定性折叠，绝不二次调 LLM（见 §3.3 D6）。

### 3.2 本步需现场拍板项（开工时先过这四条——§0 表 13）

> **2026-07-11 已裁决：四项全部按建议采纳**——轮次定义（下 1）/ `prewarm_ratio=0.8`（下 2）/
> 同步确定点执行（下 3，03 §3 已回写）/ `logger.warning` 结构化留痕（下 4，C34 细化已落 00 §2.2）。

1. **【用户拍板】"轮次"的精确定义**。建议：**一条 `user_message` 起，至下一条 `user_message` 前的最后一条 `assistant_message` 终态止，为一轮**；从 messages 投影（JOIN events 按 seq 升序）推导；轮号从 1 起、按 user 消息出现次序编；**孤儿 user 消息**（有 user 无 assistant——上次 run 中途崩溃遗留）独立成轮（assistant 视为空串），理由：用户确实说过的话是事实，不许从历史里蒸发。此定义同时被摘要覆盖范围（payload 的轮号区间）与 M2.11 验收（"第 1–5 轮埋入事实"）消费，定了就进回放断言，改=破坏历史 cassette。
2. **【用户拍板】预热阈值**。03:75 只说"接近阈值时提前做"未给数字（素材包 C.7 防脑补清单第 4 条）。建议 **0.8**（`prewarm_ratio: float = 0.8` 构造参数，可注入便于测试）：**触发量 =（既有摘要文本 token，无则 0）+ 未覆盖轮次全文 token** > 0.8 × 历史层可用预算即触发压缩（与 §4.3 算法步 3 的 `need` 逐字一致——此公式进 M2.11 确定性触发验收与回放断言，两处必须同式）。太低→摘要过勤烧 fast 档；太高→退化成"超了才压"，失去预热意义。
3. **【用户拍板】"异步预热"落地为同步确定点执行**（偏离 03:75"不阻塞当前请求"的字面）。建议：摘要在 `build()` 内部的**固定位置同步 await**，"预热"语义由"阈值 80% 提前做（而非 100% 被迫做）+ fast 档低延迟"兑现。理由：后台 fire-and-forget 任务写 `summary_updated` 事件的时机不确定 → 事件 seq 顺序不可复现 → 直接击穿 M2.12"中断-恢复事件序列逐事件一致"的 CI 强断言（回放一致性是硬约束，字面的"异步"是软优化）。真正的后台任务化列为 v2 观察项。若用户坚持字面异步，需同步设计"摘要事件允许乱序"的等价性豁免规则（进 M2.6 C31 归一化规范），代价大，不建议。
4. **【用户拍板】摘要失败的留痕方式**。C34 要求"降级+审计"；executor 的样板是把 `summarize_error` 记进**本来就要写的** `tool_result` 事件（executor.py:244-262）——但 builder 失败时**没有**顺路事件可搭（`summary_updated` 的 payload["summary"] 是投影必需键，不能写失败单）。建议：**M2 用 `logger.warning` 结构化留痕（含 session_id/run_id/异常文本），不加新事件类型**——**注意此方案构成对 C34 字面"+ 审计事件"（00 §2.2 C34 行）的偏离**，若用户采纳，须当天在 00 §2.2 C34 行登记细化（结构化日志是否算审计、或 M2.5 场景显式豁免），不许静默偏离；理由：14 类枚举钉死，为失败留痕扩枚举的收益配不上"改枚举=过口径+快照测试+回放断言联动"的代价，且下一次 build 会自动重试摘要。若用户认为必须事件级审计，则显式新增枚举成员（如 `summary_failed`）并同步 03 §5 表 + events.py 快照测试 + M2.6 归一化规范——三处联动，不许静默加。

```python
        self,
```

内部辅助（私有，包外不许依赖）：

```python

def _clip(text: str, budget_tokens: int) -> str                 # D10 确定性截断（0.8 倍循环缩短 + _CLIP_SUFFIX，参考 executor.py:79-84 思路但自带实现）
def _pack_snippets(snippets: Sequence[ScoredSnippet], budget: int, *, by_score: bool) -> str | None
```

`build()` 编排（编号步骤；本交付先实现 1、2、4、5、6、7，第 3 步历史层在交付①临时实现为"仅当前 user_input"）：

1. **system 层**：`estimate_tokens(system_prompt) > config.system_budget` ⇒ `ValueError`（D15）；产 `Message(role="system", content=system_prompt)`。
2. **长期记忆层**：`memory is None or config.memory_budget == 0` ⇒ 跳过（D14）；否则 `await memory.fetch(tenant_id=..., user_id=..., query=user_input)` → `_pack_snippets(..., by_score=True)` → 非 None 则产 system 消息 `_MEMORY_HEADER + text`（标头 token 计入层预算）。
3. **会话历史层**：见交付②。
4. **本轮检索层**：同 2，`retrieval.search(tenant_id=..., query=user_input)`、`by_score=False`、`_RETRIEVAL_HEADER`、`retrieval_budget`。
5. **当前用户消息**：`Message(role="user", content=user_input)`。
6. **工具结果层**：`working` 原样接尾；若 `Σ _message_tokens(working) > config.tool_results_budget`，从最老的 `role=="tool"` 消息起逐条把 content 替换为 `_FOLDED_TOOL_TEMPLATE.format(...)`（D6），直至 ≤ 预算或全部折叠（仍超则留余量消化 + `logger.warning`）。assistant 的 tool_calls 消息**不折叠**（`arguments_json` 是协议字段，动它会坏工具轮结构）。
7. 按 D12 次序拼 `list[Message]` 返回。

**关键不变量（交付①测试钉死）**：
- I1 输出首条恒为 system 原文，末段恒为 user_input（+working）；
- I3 provider 为 None/预算 0 时零调用（注入会爆炸的 provider 证明）；
- I4 折叠只动 `role=="tool"` 的 content，其余消息字节不变。

### 4.3 交付②：会话历史层 + 滚动摘要

内部辅助：

```python
@dataclass(frozen=True, slots=True)
class _Turn:
    index: int        # 轮号，从 1 起（拍板项 1 的定义）
    user: str
    assistant: str    # 孤儿轮为 ""
    tokens: int       # 构造时按 D16 算好

async def _load_turns(self) -> list[_Turn]        # D4 的 JOIN 查询 + 分轮
async def _summary_state(self) -> tuple[str | None, int]   # D5：(摘要全文, 覆盖游标)，无摘要 (None, 0)
async def _compose_history(self, *, user_input: str) -> list[Message]   # 下述算法，返回摘要消息+旧轮消息（不含当前 user_input 消息本身）
```

`_compose_history` 算法（编号步骤）：

1. `turns = await self._load_turns()`；`summary_text, covered = await self._summary_state()`；`uncovered = [t for t in turns if t.index > covered]`。
2. 历史层可用预算 `budget_h = config.history_budget - estimate_tokens(user_input)`；若 < 0 ⇒ `budget_h = 0` + `logger.warning`（D11，user_input 照放）。
3. `need = (summary_text 的 token，无则 0) + Σ uncovered tokens`。
4. **触发判定**：`self._summarize is not None and len(uncovered) >= 2 and need > self._prewarm_ratio * budget_h`（拍板项 2/3；D9）。
5. 命中则压缩最老 `k = ceil(len(uncovered) / 2)` 轮：

```
source = (旧摘要全文 + "\n" if summary_text else "") + 按 D8 格式拼最老 k 轮
# （2026-07-11 交付②修订：try 只包 summarize——C34 fail-open 只兜 LLM 增强层；
#   事件写入失败是事实源故障（EventStoreUnavailable，02 §5"终止本次 run"）或围栏信号
#   （EventWriteFenced，C2"终态不重试"），一律裸传播、绝不吞——吞掉会让本轮 prompt
#   引用一条不存在于事件流的摘要，击穿回放一致性。原稿把 append 一并包进 try 属笔误，
#   信任序：00 §2.2/§6.1 口径 > 本计划伪码。）
try:
    new_summary = await self._summarize(source)          # 唯一 LLM 触点；M2.7 起走 scoped("summary") 视图
except Exception as e:
    logger.warning(...)     # 拍板项 4：留痕；不写任何事件，落入步 6 确定性兜底（C34 fail-open）
    new_summary = None
if new_summary is not None:
    await self._events.append(EventType.SUMMARY_UPDATED,
        {"summary": new_summary, "turn_from": 1, "turn_to": covered + k})   # D7；投影同事务更新 sessions.summary
    summary_text, covered = new_summary, covered + k
    uncovered = uncovered[k:]
```

6. **确定性收口**（无论摘要成败都跑）：摘要自身超 `budget_h` ⇒ `_clip`；再从**最新**未覆盖轮往回累积装入（`tokens` 累加 ≤ 剩余预算），装不下即停——最老的轮被丢弃（D10）；被选中的轮按时间**正序**输出。
7. 产消息：摘要 ⇒ 一条 system（`_SUMMARY_HEADER.format(...) + summary_text`）；每轮 ⇒ user、assistant 两条原文消息（孤儿轮只产 user 条）。

**关键不变量**：
- I2 **确定性**：同一 DB 状态 + 同注入产物/钩子返回 ⇒ `build()` 输出逐字节相同（M2.12 逐事件一致与 M2.6 cassette 匹配的前提）；
- I5 只有 summarize 成功才写 `summary_updated`；一次 build 至多一条；payload 恒含 `summary/turn_from/turn_to` 三键；
- I6 覆盖游标单调递增，摘要覆盖范围与被丢弃/被压缩的轮一致——**events 原文永不受影响**（摘要只服务 prompt）；
- I7 历史层（含摘要+旧轮，不含 user_input）token ≤ `budget_h`。

## §7 陷阱与常见错误（症状 → 原因 → 正解）

1. **写 `summary_updated` 后整笔 append 炸 `ProjectionError`，事件也没了** → payload 缺 `"summary"` 键，或键名写成 `text/content`；投影契约机器强制且与事件同生共死（store.py:256-284） → payload 恒带 `summary/turn_from/turn_to`（D7），先跑 `test_summary_projection_updated_same_tx`。
2. **`ProjectionError: session=... 行不存在`** → `_project_summary` 是 UPDATE，sessions 无行 rowcount=0（store.py:261）；测试只写事件没建会话行 → helper `_seed_session` 先 INSERT `SessionRecord`（参考 tests/runtime/test_projections.py 的做法）。
3. **JOIN 查询抛 `NoForeignKeysError`** → 五表按口径**不带 FK**（00 §6.1 M2.2 行"tenant_id 等为不带 FK 普通列"，messages.event_id 同理），SQLAlchemy 推断不出关联 → JOIN 必须显式 onclause：`.join(EventRecord, MessageRecord.event_id == EventRecord.id)`。

6. **token 断言差 1–2 恒不过** → `estimate_tokens` 对 ASCII 是 `(n+3)//4` 向上取整、CJK 判定只覆盖基本区 U+4E00–U+9FFF（tokens.py:15-17），假名/扩展区不算 CJK → 测试造数据用 `"长" * k`（1 字=1 token 精确可控）；绝不引 tiktoken（C25）。
