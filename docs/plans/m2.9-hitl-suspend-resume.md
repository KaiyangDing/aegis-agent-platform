## §1 目标与定位

**做什么**：给运行时装上"人类按钮"的完整机械——① 会话锁原语落 `aegis/core/locks.py`（Redis 主 + PG advisory 降级，互斥语义在停 Redis 时也不放弃）；② 挂起链路（风险闸门命中 → 审批单 → `approval_requested` 事件 → `run_state=awaiting_approval` → 进程可下线）；③ 恢复单入口（"先取会话锁再恢复"，批准/拒绝/撤回/超时四种结局同一条路径）；④ 批准后前置校验重跑的**挂点**（校验逻辑 M3.9 注入）；⑤ 补齐闸门 #6 的 HITL 触发源（拒绝/撤回/审批超时 → `CANCELLED` 终止，M2 用可注入时钟模拟超时触发；用户取消 run 的信号路径 M2.7 已接——00 §6.1 M2.7 行"闸门 #6 本步只接取消信号与终止处理路径"，本步沿用【开工核对 K2】）。

**为什么在这**：M2.4 的执行器把 NEEDS_APPROVAL 停在"返回一个 outcome"（executor.py:151-154）；M2.2 的 ApprovalStore 把 CAS 原语备好但 create 尚无人调用——docstring 明言"调用方是 M2.9 的风险闸门命中路径"（store.py:411）；EventWriter 的单写者前提"已持会话锁"一直标注"M2.9 接电"（store.py:288）。本步把三处悬空接成闭环。

**架构与面试叙事位置**：HITL 挂起是"计划内恢复"——审批后的恢复路径与 M2.10 崩溃恢复是同一条代码路径，"日常流量天天在测灾难恢复逻辑"（03:161-162）；锁的三连问（owner token + Lua CAD / 看门狗 / Redlock 批评）是 ADR-005 面试深挖点；M2 毕业验收的**必保路径**（00 §6.2："审批回调→状态翻转→单入口恢复"全绿）与停 Redis 降级演示都出自本步。`core/locks.py` 同时是 M3.2 会话互斥（409）的复用件——写的时候心里放着两个消费者。

**范围红线**（00 §6.1 M2.9 行为权威）：不做 lease 续租/reaper（M2.10）；不做审批 API 与坐席同租户校验（M3.9）；不做前置校验的业务实现（M3.9 注入）；不做 `expire_due` 的定时调度（M3.9）；不做 SSE 提示帧（M3.10）。

### 4.1 交付①：`core/locks.py` —— 协议 + Redis 实现 + 看门狗

```python
"""会话锁原语（ADR-005 角色 5）：SET NX + owner token + Lua CAD + 看门狗续期。

Redis 主实现；PG advisory 降级（C4）；切换只在 acquire 边界。
消费者：M2.9 挂起-恢复单入口、M3.2 会话互斥（锁被占 → 409）。
"""

class SessionLockHeld(RuntimeError):
    """锁被占：上一条消息处理中 / 另一副本正在恢复。M3.2 映射 409。"""

def new_owner_token() -> str:
    """每次获取一个新 token（uuid.uuid4().hex）——释放/续期的身份凭证。"""

class SessionLock(Protocol):
    """三方法形状 + owner token 语义：release/extend 必须验 token，
    不带 token 的 DEL 会误删他人已持有的锁（ADR-005 角色 5 原文）。"""

    async def acquire(self, session_id: str, owner_token: str, *, ttl_s: float = 30.0) -> bool: ...
    async def extend(self, session_id: str, owner_token: str, *, ttl_s: float = 30.0) -> bool: ...
    async def release(self, session_id: str, owner_token: str) -> bool: ...
```

**看门狗**（挂起/恢复与 M3.2 的公共持锁形态）：

```python
@dataclass
class HeldSessionLock:
    session_id: str
    owner_token: str
    lost: asyncio.Event  # 看门狗续期失败/异常时置位——持有者应尽快收尾


@asynccontextmanager
async def hold_session_lock(
    lock: SessionLock,
    session_id: str,
    *,
    ttl_s: float = 30.0,
    renew_interval_s: float = 10.0,
    sleep: Callable[[float], Awaitable[None]] = asyncio.sleep,
) -> AsyncIterator[HeldSessionLock]:
```

编号算法：

1. `token = new_owner_token()`；`await lock.acquire(session_id, token, ttl_s=ttl_s)` → False 抛 `SessionLockHeld`；
2. 起看门狗 task：循环 `await sleep(renew_interval_s)` → `extend(...)`；返回 False **或抛任何异常** → `lost.set()` 并退出循环（**不重试、不切后端**——D13；丢锁的后果由 `(session_id, seq)` 唯一约束物理兜底）；
3. `yield HeldSessionLock(session_id, token, lost)`；
4. finally：**先 cancel 看门狗并 await 其收尾，再 `release`**（顺序颠倒会让看门狗把刚释放的锁语义搅浑，§7 坑 7）；release 的异常吞掉（Redis 挂了锁会自然过期；PG 侧 release 内部自兜底）。

关键不变量：
- 同一次持锁期间 token 不变；lost 置位后看门狗必已停止；
- `hold_session_lock` 是**唯一推荐持锁形态**——裸调 acquire/release 只允许出现在锁自身的测试里。

### 4.2 交付②：PG advisory 降级 + FailoverSessionLock（停 Redis 互斥不丢）

**PgAdvisorySessionLock（C4 修正三件套）**：

```python
class PgAdvisorySessionLock:
    """降级形态：session 级 pg_advisory_lock（非 xact 级）+ 专用连接持有显式释放
    + hashtext(session_id) 稳定哈希（Python hash() 跨副本不稳定——C4）。
    TTL 语义：PG 会话级锁无 TTL，活性 = 连接活性；extend 仅确认仍持有。"""

    def __init__(self, engine: AsyncEngine) -> None:
        self._engine = engine
        self._held: dict[str, tuple[str, AsyncConnection]] = {}  # session_id -> (owner_token, 专用连接)
```

`acquire` 编号算法：

1. `session_id in self._held` → return False（同进程占用，语义与 SET NX 对齐）；
2. `conn = await self._engine.connect()`；`await conn.execution_options(isolation_level="AUTOCOMMIT")`（AsyncConnection.execution_options 是 awaitable，sqlalchemy/ext/asyncio/engine.py:429；AUTOCOMMIT 防"idle in transaction"挂事务——会话级锁与事务无关，不需要也不能开事务）；
3. `got = (await conn.execute(text("SELECT pg_try_advisory_lock(hashtext(:sid))"), {"sid": session_id})).scalar_one()`——**try 变体**（非阻塞，锁被占返回 False → 409 语义）；哈希在 **PG 端**算（稳定哈希的落点）；
4. 未取到 → `await conn.close()`；return False；
5. 取到 → `self._held[session_id] = (owner_token, conn)`；return True。

`release` 编号算法：

1. 查 `_held`，无记录或 token 不匹配 → return False（owner 语义在应用层兜，advisory 锁本身认连接不认 token）；
2. try：`SELECT pg_advisory_unlock(hashtext(:sid))` **在同一条连接上**执行 → `await conn.close()`（此时归池安全：锁已释放）；
3. except：`await conn.invalidate()`（物理销毁连接——PG 会话死亡即释放全部 advisory 锁，这是最后保险；**绝不允许带着锁归池**，§7 坑 3）；
4. finally：`del self._held[session_id]`；return True。

`extend`：`_held` 中有记录且 token 匹配 → True，否则 False（无 TTL 可续；连接断没断交给下一次真实 SQL 暴露）。

**FailoverSessionLock**（粘滞切换，ratelimit.py:93-115 同构）：

```python
class FailoverSessionLock:
    def __init__(self, primary: SessionLock, fallback: SessionLock, *, probe_interval_s: float = 5.0) -> None:
        # self._granted: dict[str, SessionLock]  # session_id -> 授予后端；extend/release 按此路由
        # self._degraded: bool / self._next_probe: float（time.monotonic 探针窗）
```

`acquire` 编号算法：

1. 降级中且 `monotonic() < _next_probe` → 直走 fallback（粘滞：不为挂掉的 Redis 反复付连接失败延迟）；
2. 否则试 primary：**任何异常** → 首次降级打 `logger.warning`、`_degraded=True`、`_next_probe=now+probe_interval_s`，改走 fallback（与 ratelimit.py:101-110 的 `except Exception` 同宽度——锁占用是 False 不是异常，不会误降级）；
3. primary 成功且此前降级 → 打恢复日志、`_degraded=False`；
4. 任一后端授予成功 → `_granted[session_id] = 该后端`；fallback 也返回 False → return False（纯粹被占）；fallback **抛异常 → 原样上抛**（Redis、PG 双灭 = 服务不可用，与 EventStoreUnavailable 同哲学，不吞）。

`extend`/`release`：按 `_granted` 路由；无记录 → False。release 成功后清 `_granted` 条目。**持锁中途后端固定**（D13）。

```python
    async def resume(self, spec: AgentSpec, session_id: str, approval_id: str | None = None) -> AsyncIterator[AgentEvent]:
        """恢复单入口：先取会话锁再恢复（03 §5）。批准/拒绝/撤回/超时四结局统一分诊。
        approval_id 形参即 M2.10 泛化后的最终形（交接方定案，开工可复核）：非 None=审批分诊（本步实装，
        §4.3d 算法即此分支）；None=崩溃恢复分诊（分支本体 M2.10 接入，本步可先 raise NotImplementedError 占位），
        两分支共享"取锁→分诊→续跑"内部路径。"""
```

`run()` 改动：入口 `async with hold_session_lock(self._lock, session_id)`，取不到抛 SessionLockHeld（签名不变——M2 对外契约）；（按 K2/D20）循环启动 CAS idle→running、终止处理 CAS running→idle。

`resume()` 编号算法：

1. `async with hold_session_lock(self._lock, session_id)`——锁被占抛 `SessionLockHeld`（另一副本在恢复，互斥正确）；
2. 直查 ApprovalRecord（factory 开会话 select by id）；行不存在或 `approval.session_id != session_id` → 抛 `ValueError`（防串会话）；
3. 按 `approval.status` 分诊：
   - `PENDING` → 抛 `ValueError`（"先 decide/cancel/expire 再 resume"，D21）；
   - `APPROVED` → 走 4；
   - `REJECTED` / `CANCELLED` / `EXPIRED` → 走 5；
4. **批准续跑**：
   a. `transition(session_id, expected=AWAITING_APPROVAL, to=RUNNING)` → False：并发赢家已处理（坐席双击第二击）→ **安静 return，零事件**（D17/D21）；
   b. `writer = await EventWriter.open(factory, session_id, run_id=uuid.uuid4().hex)`（新 run_id，seq 接续——D16）；
   c. `yield await writer.append(EventType.APPROVAL_DECIDED, {"approval_id": ..., "approved": True, "operator_id": approval.operator_id})`；
   d. **precheck 挂点**：`self._precheck` 非 None → `reason = await self._precheck(approval.tool_name, approval.args)`；reason 非 None → 工具**不执行**（无 write-ahead），以 `f"审批已通过但前置校验未过：{reason}，操作未执行"` 作为观察结果回填模型进主循环（D19）；
   e. 通过 → `outcome = await executor.execute(approval.tool_name, json.dumps(approval.args, ensure_ascii=False), approved=True)`（重新过参数校验①；闸门③被通行证豁免——D5/D6）；
   f. `outcome.tool_call_id` 非 None → `await approvals.attach_event(approval_id, event_id=outcome.tool_call_id)`（D15）；
   g. 把 outcome.content 作为工具观察结果注入上下文，进入 M2.7 主循环续跑直至终止（重建上下文 + 续跑的内部 API 复用 M2.7 机制——**精确调用方式【开工核对 K2②】**；这条路径即 M2.10 崩溃恢复将复用的"计划内恢复"）；
   h. 终止处理沿 M2.7 既有逻辑：`loop_terminated` + `transition(RUNNING → IDLE)`；
5. **拒绝/撤回/过期终止**：
   a. 同 4a 的 CAS，输家安静 return；
   b. 开 writer（同 4b）；
   c. 按终态写对应事件：REJECTED → `APPROVAL_DECIDED{"approval_id", "approved": False, "operator_id"}`；CANCELLED → `APPROVAL_CANCELLED{"approval_id"}`；EXPIRED → `APPROVAL_EXPIRED{"approval_id"}`（03:137"审批单 id、决定人/超时"）；
   d. `LOOP_TERMINATED{"reason": TerminationReason.CANCELLED.value, ...}`（闸门 #6；payload 其余键与 M2.7 落地的 loop_terminated 形状一致【开工核对 K2⑤】）；
   e. `transition(RUNNING → IDLE)`；
   f. 全程 yield 各事件（M2.12 演示与 M3.9 API 消费）。

**"审批回调"= `ApprovalStore.decide` 本身**（D1）：M2.9 不新建回调函数；测试与 M2.12 演示直接 `decide(...)` → `resume(...)` 两步走；M3.9 的 API 层照此包装。

### 4.4 run_state 状态机全图（RunState 四值，store.py:41-47）

| # | 迁移 | 触发者 | 机制 | 接电步 |
|---|---|---|---|---|
| T1 | `idle → running` | `AgentRuntime.run()` 取锁后启动循环 | `transition(expected=IDLE, to=RUNNING)` | M2.9（若 M2.7 已接则沿用，K2④） |
| T2 | `running → awaiting_approval` | 挂起链路（NEEDS_APPROVAL，§4.3c 第 4 步） | CAS，失败=bug 裸炸 | **M2.9** |
| T3 | `awaiting_approval → running` | `resume()` 单入口（四种审批结局统一先回 running——D3） | CAS，失败=并发赢家已处理，安静退出 | **M2.9** |
| T4 | `running → idle` | 终止处理（一切 loop_terminated 原因，含 cancelled/gateway_rejected） | CAS | M2.9（同 T1 注） |
| T5 | `running → failed` | reaper 发现 `recovery_count` 超上限（C9） | M2.10 接电 | M2.10 |
| — | `failed → *` | **无**：failed 是 v1 终态（人工介入；00 未定义复活路径） | — | — |

非法迁移（`idle→awaiting_approval`、`awaiting_approval→idle` 不经 running、任何路径进 failed 除 T5、failed 出任何）一律被 `transition` 的 `expected` 参数机器拒绝——不存在"直接 SET"的入口。

> 注（交接方定案，开工可复核）：M2.10 的 LeaseStore 只管租约列、不碰 run_state（其 acquire/steal_expired 的 WHERE 以 `run_state='running'` 为前置条件，SET 不写该列；一切 run_state 翻转统一走本表 + `SessionStateStore.transition`）。**reaper 抢租不构成状态翻转（running→running），本迁移表无例外条目**。

### 4.5 关键不变量汇总

1. **锁先于写**：EventWriter 的创建点（run/resume）都在 `hold_session_lock` 之内——store.py:288 的"M2.9 接电"在此兑现；
2. 挂起后 approvals 行是唯一真相：进程可下线，重启后 resume 只凭表内状态分诊；
3. 审批事件与 run_state 变更只发生在持锁路径内：`approval_requested` 由持锁挂起链路写，决策类三事件由恢复单入口补写（D1/D7）；
4. 每个审批单至多一次恢复动作（decide CAS × 会话锁 × transition CAS 三重，D17）；
5. 批准执行必带 `approved=True` 且必回填 `attach_event`（审计链闭合）；
6. 挂起的 run 不产生 `loop_terminated`；恢复后的 run 恰产生一条；
7. 锁的授予后端持锁期间不变（D13）。

生产实现由用户届时亲手敲——本节只给签名、算法与不变量；棘手处的伪代码已控制在 15 行内。

## §7 陷阱与常见错误（症状 → 原因 → 正解）

1. **跨副本互斥"随机"失效** → 锁键用了 Python `hash(session_id)`——PYTHONHASHSEED 每进程随机，两副本算出不同键（评审 C4 点名坑） → 哈希在 PG 端算：SQL 里写 `hashtext(:sid)`，Python 侧永远只传原始字符串。
2. **PG 锁"莫名"提前释放，挂起期间互斥消失** → 用了 `pg_advisory_xact_lock`（事务级），首个事件事务 commit 即自动释放，撑不住跨多事务的整个 run（C4） → 用 session 级 `pg_try_advisory_lock` + 专用 AUTOCOMMIT 连接。
3. **PG 锁永远释放不掉，重启应用才好** → 专用连接没 unlock 就 `close()` 归池——advisory 锁跟着 DBAPI 连接活着，池里那条连接带锁复用/闲置 → release 顺序：同连接显式 `pg_advisory_unlock` → 再 close；unlock 抛异常时 `await conn.invalidate()` 物理销毁连接（PG 会话死亡即释放锁）。
4. **PG 互斥测试全绿但其实什么都没测** → 两次 acquire 走了同一条连接——session 级 advisory 锁对同一 PG 会话**可重入**（重复获取计数 +1），假绿 → 互斥断言必须用两个独立引擎/连接（NullPool）；`db_conn` 夹具是单连接，不可用于互斥测试。
5. **CAD 释放永远 False，锁只能等 TTL 自然过期** → Lua 里 `GET` 返回值与 ARGV 比对时 bytes vs str 不齐——自建客户端漏了 `decode_responses=True`（get_redis() 单例有，core/redis.py:17） → 锁客户端一律走 `get_redis()`；测试自建客户端照抄 conftest 的 `decode_responses=True`。
6. **`set(..., px=...)` 抛 DataError 或静默截断** → px 要毫秒**整数**，传了 `ttl_s * 1000` 的 float → `px=int(ttl_s * 1000)`；Lua PEXPIRE 的 ARGV 同理转 `str(int(...))`。
7. **释放后锁又"复活"，下一个获取者立刻被挤掉** → 看门狗任务没先 cancel 就 release，任务在 release 之后又跑了一轮 extend（虽然 CAD 会失败，但异常路径日志噪音大且时序不定） → finally 固定顺序：cancel 看门狗 → await 其收尾 → release。
8. **看门狗测试在 CI 偶发红** → 用真实 sleep/计时做断言——时序敏感断言不进 CI（00 §2.2 测试纪律） → 注入 sleep 缝（构造参数 `sleep=`，与 EventWriter/executor 同款接缝），断言"调用了几次 extend"而非"过了几秒"。
9. **写 approvals 时 asyncpg 抛 `can't subtract offset-naive and offset-aware datetimes` 或列值时区错乱** → `expires_at` 用了 naive `datetime.now()`——列是 `DateTime(timezone=True)`（store.py:163） → 一律 `datetime.now(UTC)`（test_approvals.py:12-13 同款）；进事件 payload 时 `isoformat()` 成字符串（JSONB 不收 datetime 对象）。
10. **恢复后又生成一张审批单，会话在挂起里打转** → resume 执行工具时忘了 `approved=True`，执行器再次命中风险闸门返回 NEEDS_APPROVAL → 单入口的批准执行**必须** `execute(..., approved=True)`（D5）；测试 `test_resume_approved_executes_and_completes` 的事件序列断言会当场抓住。
11. **挂起时多写了一条 `loop_terminated`，回放对账（M2.12）炸** → 口径误读：把"loop 干净退出"理解成"终止" → 挂起≠终止（D2）：TerminationReason 无 suspended 成员，枚举冻结改值=破坏重放（spec.py:24-25）。
12. **在 decide 回调里顺手写事件、翻 run_state** → 照抄 03:157 的旧括号表述——它与 store.py:394-395 冲突，代码为准（D1，文末问题#1） → 回调只 `decide`；事件与状态全部在持锁单入口。
13. **顺手实装 lease 续租 / reaper / 审批 API / expire_due 定时任务** → 越步：lease/reaper 是 M2.10，审批到期扫描调度与坐席 API 是 M3.9（00 §6.1 M2.9 行明示"reaper 到期扫描实装在 M3.9"——活文档不引裸行号） → 本步对超时只做"可注入时钟单测"；`sessions.lease_*` 列一个都不碰。
14. **凭记忆用 `redis.asyncio.lock.Lock` 或手搓 Redlock** → 弱模型高发"凭记忆写接口"：内置 Lock 的 token/阻塞语义与 ADR-005 叙事不合，Redlock 被 ADR-005:54 明示"单实例场景不需要" → 按 §4.1 自研三方法 + 两段 Lua；写前 Read ratelimit.py:79 学 register_script 用法。
15. **"停 Redis 验证"去 docker stop，CI 直接挂** → CI 的 Redis 是 service 容器，测试停不掉 → 用 `dead_r` 夹具（无人监听端口 + 0.1s 超时，conftest.py:28-39）；真停容器演示归 M2.12/M5.4（D14）。
16. **落盘凭证/脚本输出中文乱码或 UTF-16** → PowerShell 5.1 默认编码坑（06 §4.3，M2.0 实测踩中） → `[Console]::OutputEncoding` 钉 UTF-8 + `$env:PYTHONUTF8="1"`；落盘用 `Out-File -Encoding utf8`，或直接用 pwsh 7。
