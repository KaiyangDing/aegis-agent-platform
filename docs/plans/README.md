# plans · 步骤级详细计划目录（消费规则）

> **地位**：本目录是 00-master-plan §6–§9 各步骤行的**展开层**——把每一步展开到
> 文件级/类级/签名级，供接续模型（Opus/Sonnet 等）执行时消除脑补空间。
> 写作基线：**M2.4 毕业时点**（commit `014ec21`，301 测试全绿，2026-07-10）。
> 计划由 Fable 5 在交接前一次性撰写并经代码级对抗校验；此后由当班模型按下述纪律维护。

## 1. 消费方式（开工某一步时）

1. 读 00-master-plan 中该步骤的表格行与所在里程碑章节（步骤行是**权威范围**，计划文件不得扩权）；
2. 读本目录对应计划文件**全文**；
3. **强制执行文件开头的「§0 开工核对清单」**——逐项 Read 真实源码核对签名/常量/测试数，
   任何一项对不上：先停下，把差异报给用户并修订计划，再动手；
4. 按 00 §2.1 协作规约交付（生产代码用户敲、测试 AI 直写、四件套、一次一步）。

## 2. 信任序（冲突裁决，与 CLAUDE.md 第 4 条一致）

**实际代码 > 00 §2.2 口径表 > 本目录计划 > 02/03/04 设计文档叙述。**

- 计划文件写作时已对账过 M2.4 基线，但**它描述的未来会被先落地的步骤改变**——
  这正是 §0 开工核对清单存在的原因；
- 发现任何两层之间的冲突：当天修订低层文档，并在 00 §10.1 登记（若涉及口径则进 §2.2）；
- 计划中引用的「素材包 / pack-*」是交接期一次性工作件（**未随档落盘**）——引用仅供溯源，
  事实一律以源码与 `docs\08-code-map.md` 为准，不要去搜索这些文件。

## 3. 计划文件统一模板（每份文件都是这 10 节，缺节视为文件损坏）

| 节 | 内容 |
|---|---|
| §0 开工核对清单 | 动手前必须逐项核实的事实（文件/签名/常量/测试收集数）+ 核对命令 |
| §1 目标与定位 | 本步做什么、为什么、在三层架构与面试叙事中的位置 |
| §2 契约事实源 | 本步**消费**的既有接口（原样签名+出处）与**提供**给后续步骤的接口（缝的两端） |
| §3 设计决策与口径 | 已裁决决策（出处）/ 本步需现场拍板项（标【用户拍板】并附建议）/ 关联 00 §2.2 条目 |
| §4 实施蓝图 | 新建/修改文件清单；按交付①②③切分；类与函数**精确签名**、算法编号步骤、关键不变量；只在必要处给伪代码，不给整段实现（防漂移，实现在会话内交付） |
| §5 测试蓝图 | 按测试文件列测试函数名与断言要点；fixture 复用/新增；预期新增测试数（区间） |
| §6 验收对账清单 | 复选框清单 + pytest 收集数核对法 + 与 00 该里程碑毕业验收汇总的对应项 |
| §7 陷阱与常见错误 | 本步特有的坑（环境/库行为/口径误读/弱模型高发错误），每条给"症状→原因→正解" |
| §8 指令块模板 | 交付时给用户的标准指令块（ruff format → ruff check → pytest -q → mypy . → lint-imports → git add/commit/push）+ 各命令预期输出 |
| §9 完成后动作 | 00 文档更新点、计划文件偏差回填、深挖题登记 `interview-questions.md`、记忆更新时机 |

## 4. 维护纪律

- 步骤毕业当天：由当班模型在该计划文件**头部**登记「实际落地偏差」块
  （无偏差也要写"无偏差"），并同步 00 §6.3/§10.1；
- 某计划中的决策被现场推翻：当天改计划文件 + 00 登记，**不许只改代码不改文档**；
- 本目录文件**只增改不删**；被砍的步骤在文件头标注「已裁剪，见 00 §11」。
