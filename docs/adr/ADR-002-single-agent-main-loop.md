# ADR-002 · 主链路单 Agent + 受限子 Agent，而非多 Agent 协作

**状态**：Accepted　**日期**：2026-07

## 背景

多 Agent 协作（规划者/执行者/审查者分身）在 2024–2025 被大量炒作，
但工业界实践给出了更冷静的结论：
- Cognition《Don't Build Multi-Agents》：多 Agent 间上下文不共享导致信息丢失与相互矛盾，
  错误级联放大，写/动作密集任务上单 Agent 一致性显著更好；
- Anthropic 多 Agent research 系统的经验：**读密集、可并行**的任务（大规模检索、调研汇总）
  多 Agent 有真实收益，代价是 token 消耗数倍增长。

客服主链路是典型的"动作密集 + 需要全程一致性"场景：理解、检索、调工具、确认、回复
必须共享同一份上下文。

## 决策

1. 主链路：**单 Agent（ReAct 循环）+ 工具**，全程一份上下文；
2. 意图路由是一次小模型分类调用，**不是 Agent**（无循环、无工具）；
3. 运行时保留 spawn 只读子 Agent 的能力，仅用于"读密集可并行"场景
   （复杂工单的并行调查——同时查订单系统/知识库/历史工单再汇总）。
   **落点**：接口已预留（`AgentSpec.sub_agent_policy`，v1 恒为 DISABLED，见运行时详设 §1），
   实现列入路线图"v2 展望"——承诺与排期对齐，不留悬空；
4. LLM-as-judge 用于离线评测，不进在线链路。

## 备选方案

- **全多 Agent 编排（planner/executor/critic）**：token 成本 3–5 倍，调试难度指数上升，
  客服场景收益无法覆盖代价；
- **纯单 Agent 永不扩展**：放弃了并行调查这类真实受益场景，运行时能力不完整。

## 后果

- 收益：主链路可调试、可预算、行为一致；子 Agent 能力存在但被架构约束（只读、限深度 1 层）；
- 代价：单 Agent 的上下文管理压力更大——这正是 ContextBuilder 要解决的问题（运行时详设 §3）。

## 面试深挖点

- "为什么不用多 Agent"比"我用了多 Agent"更能体现工程判断；
- 子 Agent 为什么限制只读：写操作跨 Agent 的事务一致性无解，读操作天然可并行可丢弃；
- 如果面试官追问"什么时候该用多 Agent"：任务可分解为互不依赖的子查询、单上下文装不下、
  且对延迟不敏感对成本不敏感——三个条件同时满足才考虑。
