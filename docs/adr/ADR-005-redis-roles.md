# ADR-005 · Redis 作为共享基础设施（一个组件六个角色）

**状态**：Accepted（v1.1 评审修订）　**日期**：2026-07

## 背景

API 层要水平扩展就必须无状态，所有跨副本共享的运行时状态需要一个低延迟的
集中存储。引入组件要克制——每多一个组件就多一份运维与故障面。

## 决策

用单一 Redis（开源 Redis 7 核心，**不依赖 Redis Stack 模块**）承担六个角色：

| # | 角色 | 实现要点 |
|---|---|---|
| 1 | 会话运行时状态 | 活跃会话热数据（冷数据在 PG）；副本无亲和性 |
| 2 | 精确缓存 | key = `tenant_id + prompt_hash`（租户强制隔离）→ 回复体。**语义缓存列 v2，且其向量索引放 pgvector 而非 Redis**——开源 Redis 7 核心没有向量检索能力（需 Redis Stack 或应用层暴力扫描），且 pgvector 方案天然获得 tenant 过滤与 TTL 列，与 ADR-006 单库叙事一致；语义缓存查询前置一跳 query embedding（几十到几百 ms + 配额），此成本计入设计，也是 v1 先不做它的理由之一 |
| 3 | 分布式限流 | 令牌桶，Lua 脚本保证读-改-写原子性；供应商/租户两维度（出站层） |
| 4 | Celery broker | 摄取流水线的任务队列 |
| 5 | 分布式锁 | 会话互斥。**完整语义**：SET NX + 过期 + 看门狗续期获取；释放必须带 owner token 用 Lua compare-and-delete（不带 token 的 DEL 会误删他人已持有的锁——比 Redlock 更基础的必考题）。锁被占时的行为写死：返回 409"上一条消息处理中"（pending 队列列 v2） |
| 6 | 熔断器共享状态 | 多副本同时感知供应商故障；半开探测用 SET NX 抢令牌互斥，防惊群 |

## 备选方案

- **进程内存**：单副本可用，`--scale api=3` 即失效——限流变 3 倍配额、熔断各自为政、会话锁失效；
- **全放 PostgreSQL**：功能可行，但限流/锁这类每请求多次的操作会把连接池打满；
  PG 管持久事实，Redis 管易失协调；
- **专用组件拼盘**（RabbitMQ + etcd + Memcached）：能力更强但单人项目运维不起。

## 后果

- 收益：架构简单，跨副本行为一致；六个角色构成完整面试叙事线；
- 代价：Redis 成为泛化依赖。**降级预案（评审后逐项写实）**：
  - 限流/精确缓存 → 本地内存模式，**本地配额 = 全局配额 / 副本数**（牺牲精度保总量）；
  - 熔断器 → **fail-open + 本地计数**：Redis 不可用时不再共享跨副本熔断状态，放行请求、
    以进程内计数维持基本保护——熔断是可靠性闸门不是安全闸门，宁可放行不误杀全量流量
    （M1.12 实装、停容器实录通过；2026-07-07 评审 C17 补录——04 路线图早已声明"语义补进
    ADR-005"而本文档漏写，本条即兑现该同步）；
  - 会话互斥 → **降级为 PG advisory lock**（PG 本就在链路上）——保住互斥语义，而不是
    "尽力而为"地放弃它。**语义要点（2026-07-07 评审 C4 修正）**：必须用 **session 级**
    `pg_advisory_lock`（专用连接持有、结束显式 `pg_advisory_unlock`），不能用事务级
    `pg_advisory_xact_lock`——后者在首个事件事务提交时即自动释放，撑不住跨多事务的整个
    run；锁键必须用**稳定哈希**（如 PG `hashtext(session_id)`），不能用 Python `hash()`
    ——其随 PYTHONHASHSEED 每进程随机，跨副本算出不同键，互斥直接失效；
  - Celery 任务 → v1 接受**摄取与 reaper 恢复调度一并暂停**（broker 即 Redis，beat/reaper
    随之停摆——已接受的降级面，Redis 恢复后自愈；outbox 补投列 v2 展望，不假装已有。
    2026-07-07 评审 C7 落档：此前"停 Redis 核心链路不断"的叙事未点名这一项）；
  - 核心对话链路不因 Redis 宕机中断（演示：停 Redis 容器）；
- 生产环境应上哨兵/集群，本项目单实例 + 文档说明（刻意的范围裁剪）。

## 面试深挖点

- 锁释放安全：owner token + Lua CAD 是第一问；锁过期任务没跑完是第二问（看门狗续期）；
  Redlock 是第三问（单实例场景不需要，且 Redlock 本身有争议——能提 Kleppmann 的批评更佳）；
- 限流为什么用 Lua：GET+SET 两步间有竞态，Lua 服务端原子执行；
- 缓存与 PG 一致性：本系统缓存全部可丢（cache-aside + TTL），不存在双写一致性难题——
  主动指出"我的场景不需要解决这个问题"也是加分项；
- 为什么语义缓存不放 Redis：版本能力（Redis 7 核心无向量检索）+ 租户隔离实现成本 + 已有 pgvector。
