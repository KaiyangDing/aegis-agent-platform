# ADR-001 · 为什么需要平台层，而不是直接调用大模型

**状态**：Accepted　**日期**：2026-07

## 背景

大模型 API 是无状态的文本补全服务：不了解企业私有数据、不能执行动作、
不保证可用性、按 token 计费无上限、对输入不设防、行为变更无法量化检测。
企业应用的要求恰好全部落在这些空白处。

## 决策

在 LLM API 之上构建三层平台（网关/运行时/业务），把"智力"与"生产系统"之间的
全部差距工程化：数据（RAG+隔离）、行动（工具+HITL）、状态（会话+事件流）、
可靠（重试/熔断/fallback/兜底）、成本（路由/缓存/预算）、安全（注入防护/脱敏/审计）、
质量（评测回归）、可观测（trace/指标）。

## 备选方案

1. **直接调 API + 少量胶水代码**：原型可行；生产上任何一次上游抖动、一个诱导死循环的
   用户输入、一次 prompt 改坏都会直接变成事故，且无法定位；
2. **采购 SaaS Agent 平台（Coze/Dify 类）**：可行的商业选择，但数据出域、深度定制受限、
   成本不可控；且对本项目而言，"用平台"不构成简历能力证明，"造平台"才构成。

## 后果

- 收益：每一类生产问题有明确的模块归属和量化验收；换模型/换供应商是配置变更；
- 代价：前期工程投入大（约 10–11 周，见路线图），平台代码量远超业务代码量——
  这与 Sculley 等人在《Hidden Technical Debt in Machine Learning Systems》(NeurIPS 2015)
  中"ML 代码只是真实系统中很小一部分"的经典论断同构（类比引用，非本项目实测数字）。

## 面试深挖点

- 类比：LLM 是 CPU，平台是操作系统——CPU 不负责进程调度、内存保护和权限，OS 才负责；
- 反问自答："那 OpenAI/Anthropic 自己会不会把这些都做了？"——供应商在补基础件
  （结构化输出、缓存、批处理），但数据隔离、业务工具、HITL、成本治理、跨供应商容灾
  天然只能发生在企业自己这一侧。
